## 1. 产品定位

面向个人的技能成长管理软件，重点不是自动安排日程，而是让用户**主动决定学什么、做什么、投入多久、如何评价成果**。系统负责记录、结算、展示与统计。

核心闭环：**手动创建技能 → 手动创建任务 → 一次或多次专注 → 结算成功/失败 → 经验升级 → 解锁职业/称号 → 查看日志与统计**。

## 2. 用户可手动管理的对象

| 对象 | 最小能力 |
| --- | --- |
| 技能树 | 新建、重命名、设置主题、排序、归档 |
| 技能 | 新建、编辑、删除/归档、设置图标、创建子技能、查看等级/XP |
| 技能关系 | 添加/移除父子关系、前置依赖、普通关联；跨树引用 |
| 任务 | 新建、编辑、关联多个技能、设置每个技能的成功奖励等级、结算成败、重试 |
| 专注记录 | 正计时、倒计时、番茄钟；暂停/继续/结束；关联技能和可选任务；历史补录 |
| 职业 | 手动定义职业阶段、条件、可选分支；满足条件后由用户确认转职 |
| 称号 | 手动定义或启用内置称号条件；解锁后选择佩戴 |
| 日志 | 查看、筛选、追溯每一次经验变化和任务尝试；必要时撤销错误结算 |

不需要：**周期待办、任务/技能模板、自动创建日程**。不以 AI、社交排行、商城、装备掉落等作为首版前提。

## 3. 技能树

### 3.1 组织关系

- 一个技能属于一棵技能树；可以有一个父技能，形成层级；**父子关系仅在同一棵树内**。
- **前置依赖**不是父子关系。示例：`REST API Lv.5` 是 `Go 服务开发` 的前置；前置技能可以来自**另一棵技能树**。
- **普通关联**是参考/推荐关系，不产生硬性解锁条件；支持跨树。
- 技能间关系可在**技能详情右侧 Drawer**中创建或移除。创建子技能时自动填入父技能，添加前置时可搜索其他树和技能。
- 展示层以**固定/自动排布**为主，不要求用户自由拖拽画布；支持缩放、平移、聚焦、跨树跳转。
- 默认前置依赖采用**全部条件满足**才显示已解锁；创建和编辑不受锁定状态限制。采用**软锁定，仅影响解锁展示与引导**，允许记录专注和获得任务奖励。

### 3.2 图标

- 从可搜索的**固定图标库**中手动选取，创建后可更换；**不随机**。
- 原生客户端使用 SF Symbols / 自带资源映射；数据库保存独立的 `icon_key`（例如 `terminal`、`database`），避免直接绑定平台符号名称。
- 无图标时用固定默认星标；**经验环、光效、锁定边框**由数据状态决定，不改变图标本身。

## 4. 经验与等级

### 4.1 规则

- 计时有效时长以**秒**持久化，跨多次会话累计，避免丢失不足一分钟的部分。
- 以技能维度累计总有效秒数，`time_xp = floor(total_effective_seconds / 60)`。
- 任务成功时的自定义奖励：关联技能可以各自设置 `reward_levels`，单次奖励 `reward_levels × 60 XP`；该技能累计 `task_xp` 为奖励之和减去对应撤销补偿。
- `total_xp = time_xp + task_xp`；**初始 Lv.1**，则 `level = 1 + floor(total_xp / 60)`，经验进度 `total_xp % 60 / 60`；撤销按第 5 节保留原始奖励与反向记录。
- 示例：Go 已有 40 XP，专注 30 分钟后为 70 XP（Lv.2，10/60）；成功完成奖励 +2 级的任务后为 190 XP（Lv.4，10/60）。
- XP 由后端按原始记录权威结算；客户端可以提供即时预览。重试上传不能重复加 XP。
- **时间贡献与任务奖励分别统计**；仅将已有专注关联到任务，不重新发经验。

### 4.2 多技能任务和多次专注

- 一个任务可以关联任意多个技能；每个关联技能有独立的**成功奖励级数**，默认为 0。
- 一个任务可累计**多次专注**，每次专注确定一个**主技能**，仅向该技能累计时间 XP；避免一段时间在多个技能重复计分。
- 计时可以不关联任务（自由专注），稍后再绑定一个任务；该操作只更新任务关联，不改变累计时间与经验归属。
- 任务累计时长 = 所有关联且已结算专注记录的有效时长总和，任务详情列出每次记录。

## 5. 任务状态与成功率

建议状态：`待开始`、`进行中`、`成功`、`失败`、`取消`。用户手动确认成功、失败或取消；到期只显示逾期，不自动判失败。

- **成功**：记录一次成功尝试；发放该尝试的任务奖励。成功后不再次自动结算。
- **失败**：记录一次失败尝试；不发完成奖励，保留此前专注时长与 XP；可以填写失败原因。
- **重试**：为相同任务开启**新的尝试**，历史失败不被覆盖；之后成功/失败分别追加新记录。
- **取消**：不进入成功率分母；与失败区分。
- 成功率 = `成功尝试次数 /（成功尝试次数 + 失败尝试次数）`；没有已结算尝试时显示“暂无数据”，不显示 0%。
- 按结算时间统计每日/每周/每月成功率；支持按技能树、技能、任务筛选。任务关联多个技能时，按技能筛选可包含这次尝试，但汇总去重以尝试 ID 为准。
- 错误结算可执行**撤销**，通过补偿记录修正奖励和统计，不直接改写历史事件。

## 6. 专注模式

| 模式 | 规则 |
| --- | --- |
| 正计时 | 从零开始，手动暂停/结束，累计实际有效时长 |
| 倒计时 | 设置目标时长，可提前结束；只计算实际有效时长 |
| 番茄钟 | 配置专注/休息时长和轮数；只有专注阶段增加有效时长和 XP |

- 支持暂停、继续、结束、关闭窗口后继续、重开后恢复现场；进程退出、系统休眠和重启之间的计时边界须按 Q06 明确，不能将未观察时段直接当作有效专注。
- 不以界面 `Timer` 的滴答次数作为最终时长来源，使用系统时间锚点 + 持久化累计时长计算。
- 到点发送本地通知；休眠/恢复策略独立处理，避免错误计算睡眠时间。
- 一段专注结束后**不自动代表任务成功**，任务成功/失败由用户单独确认。
- 结束会话后保存记录并在联网时上传；网络断开不丢失，重试使用同一个会话 ID。

## 7. 职业转职与称号

**职业/转职**是成长路线和身份阶段：如“开发学徒 → 前端开发者 → 性能专精”或“全栈开发者”。

- 条件首版支持：技能等级 ≥ N、技能真实专注时长 ≥ N、任务成功次数 ≥ N、指定任务成功。
- 条件默认全部满足；跨技能树引用技能可作为条件。
- 达标后显示“可转职”，必须由用户**主动确认**；保留原始技能等级和历史职业记录；可支持分支路线。
- 首版职业不提供等级加成或复杂属性系统，避免影响 XP 简单规则。

**称号**是独立于职业的收藏与展示，如“百小时修炼者”“越挫越勇”“十战九胜”。解锁后可选一个佩戴；支持手动创建名称、图标、描述和条件。成就页展示已解锁、可解锁和锁定状态。

## 8. 事件日志与统计

日志类型至少包括：技能创建/编辑、任务创建/状态变化、计时开始/暂停/结束、XP 变动、等级提升、任务尝试成功/失败、撤销、转职、称号解锁/佩戴。

统计维度至少包括：累计/每日/每周专注时长、按技能投入、XP 来源拆分、任务成功率、失败次数、任务重试次数、职业与称号历史。可以从图表跳转到对应原始日志。

## 9. 首版不做与后续可选

- 不做周期任务、不做模板、不做随机图标、不做自由节点拖拽、不强依赖 AI。
- 首版用户数据在线编辑、离线**专注可持续记录**；不立即实现所有实体的复杂离线合并。
- 后续可做：更丰富的转职条件、更多粒子动画、iOS 版、Android 原生版、离线任务编辑和冲突处理。

上述后续方向是可选范围，尚未成为已确认的后续实施事项，不进入 TODO。职业/称号的基础规则与交互仍属于本次首版；任务优先级 P1 只表示顺序，不免除验收。

## 10. 数据、权限与交付边界

- 从首个领域 API 开始校验身份及资源归属；用户 A 不得通过传入用户 B 的树、技能、任务、会话或尝试 ID 读取或修改 B 的数据。账号方案见 Q02。
- 原始有效秒数、尝试结果、奖励快照及补偿记录是可追溯事实。重复请求不能重复计分；新增成功记录、各技能奖励和对应事件必须原子提交。
- 首版采用在线实体编辑、离线专注与只读缓存；账号切换不能将旧账号队列发给新账号，也不能静默丢弃待上传记录，保留/恢复规则按 Q02 执行。
- 技能删除/归档涉及子技能、关系、历史会话和奖励引用；按 Q08 保留历史并限制删除。当前本机持久卷已有受控验收数据，不能删除或重建卷来规避迁移。
- 保留原 M9 的用户说明、数据导出/备份入口和 macOS 打包义务，格式和分发渠道分别由 Q11、Q12 决定；导出成功不能代替备份可读取性验证，也不自动增加数据恢复导入功能。
- 本机 Docker 部署与本机签名安装已获授权；公网发布、商店提交及外部签名凭据操作仍需对应授权。按 Task 中各门禁记录实际验收。

### 11.2 仍需核验的条件

## 12. 验证策略与风险

| 验证层级 | 证明的内容 | 入口及边界 |
| --- | --- | --- |
| 规划静态检查 | 文档链接、稳定 ID、依赖无环、AC/场景与执行责任完整 | 本轮实际执行；不证明业务已经实现 |

主要风险包括计时恢复不可观测区间、并发结算与补偿、账号队列归属、历史引用删除及成就回退。分别由 Q06、Q07、Q02、Q08、Q09 和对应任务处理；缺少决策或环境时保留阻塞，不能降低验收标准。SwiftData 不满足系统范围时可评估 SQLite；身份和分发各选择一个已明确方案，不提前引入多方案兼容层。
